# Context Circuit 2.0.0-rc.9

A candidate for 2.0.0-rc.8 that changes where workspace behavior is written, not
what it says. No command changes, no record changes shape, no configuration file
moves, and nothing is converted for you. The v2 description in 2.0.0-rc.1 still
stands. This template recommends CLI `2.0.0-rc.9`. Git is required. No Go or
Python runtime is.

## The entry instruction now carries only what must always be in force

`AGENTS.md` goes from 348 lines to 201. What stays is the gates — what needs a
person — and the standing prohibitions — what is never done without one:

- the intent approval gate, and that a request for a change is not consent to
  the intent derived from it;
- that execution starts on a request and never before one, and that worktree
  preparation is part of that request rather than a second gate;
- that commit, push, pull-request creation, merge, deployment, publication, and
  deletion each require explicit authorization;
- that a plan is not edited by running it, that failed and partial work is
  preserved, and that no automatic repair loop or independent verification
  starts during execution;
- the attribution ban.

A rule written there is in force whether or not a skill was loaded. That is the
line the split is drawn on: a prohibition can never become a skill, because
nothing makes an agent load the do-not-push skill before pushing.

## Ten skills, one per stage

`cc-cli` and `cc-dispatch` already existed. Eight are new:

| Skill | Carries |
| --- | --- |
| `cc-workspace` | initializing, connecting or cloning repositories, members and allocation bands |
| `cc-intent` | writing an intent, its body fields, and the numbered open questions |
| `cc-plan` | creating plan records from an approved intent, and what a plan holds |
| `cc-worktree` | preparing a worktree, choosing its start, and the environment reuse report |
| `cc-stacked` | running several plans at once, integrating each wave, where to stop |
| `cc-review` | independent read-only review when a person asks for one |
| `cc-knowledge` | writing notes, their anchors, catalog entries, and the glossary |
| `cc-complete` | marking plans completed and judging the knowledge to reconcile |

`cc-dispatch` also absorbed the judgment about *when* delegating a planner or
explorer is worth it, which sat apart from the skill describing how.

Claude Code and Cursor get a routing file under their own skill directory, as
`cc-cli` and `cc-dispatch` already did. Every other host, including Codex,
reaches a skill because the entry instruction names its path — which is why each
skill costs a resident line there, and why the split is by lifecycle stage
rather than by topic.

## What made each stage safe to defer

Either a word a person actually says before it — "run these plans", "review
this", "initialize", "add a member" — or a command that names the obligation in
its own output. `setup_required`, `planning_required`, and `reconcile_required`
deliver the pointer at the moment the work comes due, which is what lets the
procedures behind those gates live outside an always-loaded document.

The knowledge-writing conventions have the weakest trigger of the set. They are
deferred anyway because `check` reports a note that crosses them, so a skill
that was never loaded produces a caught error rather than a silent one.

## The reference layer is reachable again

`.context-circuit/docs/` ships five files. Two of them — the workspace file
contract and the record structures — were named by nothing an agent loads, only
by `README.md`, which a person reads. They are now named where they are
relevant, and a test asserts that every shipped skill and doc is reachable from
the entry instruction, directly or through a skill it names.

## Upgrading

Install the CLI, then take this release's `AGENTS.md` and the `.agents/skills/`,
`.claude/skills/`, and `.cursor/skills/` trees into the workspace. A workspace
that pulls the template repository gets them with the release; one that does not
can write the blank seed elsewhere and copy those paths across:

```sh
context-circuit-cli --workspace <root> template export --path /tmp/cc-2.0.0-rc.9
```

An `AGENTS.md` you customized needs merging rather than replacing — your edits
are in a file that this candidate rewrote substantially.

`agent setup` is not required: subagent role definitions and the instructions
they embed are unchanged since 2.0.0-rc.8. No records are rewritten, and a
workspace left on the previous candidate keeps working with its previous
instruction.

## Candidate status

Deterministic tests cover the layering rather than the prose: every shipped
skill is named by the entry instruction, every shipped doc is reachable from it
or from a skill it names, the general implementation rules stay in the entry
instruction and out of `cc-stacked`, and the gates and prohibitions are asserted
present in the entry instruction by name. Every fenced example in every skill is
now executed against a real workspace, where before only `cc-dispatch` was.

The content was checked for loss mechanically — each sentence of the previous
entry instruction was matched against the new entry instruction plus all skills —
and one dropped sentence was restored.

What no test here establishes is the premise. The two failures this project has
actually observed were in material that stays resident, and both were fixed in
2.0.0-rc.8 by making the command say what it had just made due, not by moving
text. This candidate is a bet that an agent follows a shorter always-loaded
document more reliably than a longer one, and that each stage's procedure is
retrieved when its stage arrives. Neither half is measured. The failure mode it
introduces is the opposite of the one it removes: a skill that is not loaded is
a rule that is not merely skimmed but absent. Exercise the flows you rely on
before depending on this release.
