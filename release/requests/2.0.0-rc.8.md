# Context Circuit 2.0.0-rc.8

A candidate for 2.0.0-rc.7 that changes what three commands say and nothing about
what they do. No record changes shape, no configuration file moves, and nothing
is converted for you. The v2 description in 2.0.0-rc.1 still stands, and the base
branch that moved to the machine's own binding in 2.0.0-rc.7 stays where it is.
This template recommends CLI `2.0.0-rc.8`. Git is required. No Go or Python
runtime is.

## A base branch is reported where a repository is

Moving `base_branch` out of `workspace.yaml` in 2.0.0-rc.7 left a value of the
same shape behind in the file everyone shares. Asked which branch to open a pull
request against, a coordinator read `default_branch` from that file, answered
confidently, and targeted the wrong branch. The value it wanted was stored, was
consumed by worktree preparation and order derivation, and was printed by
nothing.

`base_branch` now appears beside the checked-out branch in `status`, `repo
inspect`, `worktree prepare`, and `worktree inspect`. Seeing the two together is
what separates the branch this work returns to from the branch it happens to sit
on. A binding that records no base still falls back to the repository's shared
default, and the reported field says which answer you are getting.

The entry instruction now names `base_branch` and the commands that report it as
the pull-request target, and says plainly that `workspace.yaml`'s
`default_branch` is the repository's default rather than what this machine
delivers to.

## Approval and completion name the work they leave open

Both gates hand work back rather than finish it, and both were read as finished.

`record complete` already returned the catalog entries scoped to the plan's
repositories. A coordinator marked a plan done, ignored them, and reported that
completion does not touch context files — true of the command, false of the
request, and four notes were reconciled an hour later. A list under a key called
`completed` reads as information. It now arrives with `reconcile_required`
naming the outstanding act whenever there are entries to judge: a candidate set
to judge, never a list to rewrite.

`record approve` answered with `ok: true` and nothing else. A coordinator
approved an intent, stopped there, and created no plan; asked why, it said it had
stopped after approval instead of continuing with the code investigation and plan
creation. The rule was in the entry instruction, in context, and unfollowed —
what the command said was that the request had succeeded. Approval now returns
the approved ID and `planning_required`, naming the planning it just authorized
and the stop that follows it.

Both follow `setup_required` on a dispatch: a field whose name is the obligation,
arriving at the moment that obligation comes due. The entry instruction still
carries the rules; the output is what makes them arrive on time.

## Changed output

`record approve` no longer returns the generic `{"operation", "workspace", "ok"}`
result. It returns `{"approved", "planning_required"}`. A caller testing `ok` on
an approval sees no such field; a failed approval still exits non-zero and prints
its error, which is how every other command reports failure. `record complete`
gains a key and loses none.

## Upgrading

Install the CLI and continue. No workspace file changes, no `agent setup` is
required for this candidate — subagent instructions and role definitions are
unchanged since 2.0.0-rc.7 — and no records are rewritten.

A workspace still running 2.0.0-rc.7 keeps working; it simply gets the older
answers, which is the whole subject of this candidate.

## Candidate status

Deterministic tests cover the reported base branch through `status`, `repo
inspect`, `worktree prepare`, and `worktree inspect`, including the binding that
records one and the binding that falls back to the shared default; the
completion result that names `reconcile_required` when candidates exist and omits
it when there are none; and the approval result that names the approved intent
and the planning it authorized. The entry instruction's parity with the shipped
command reference is covered as before.

Whether a coordinator that reads `planning_required` then actually plans, or one
that reads `reconcile_required` then actually judges each entry, is established
by no test here. These are instruction changes delivered through command output
rather than through an always-loaded document, which is a change of where the
sentence arrives and not a guarantee that it is acted on. The evidence that
motivated them is two observed sessions, not a measurement. Exercise the flows
you rely on before depending on this release.
