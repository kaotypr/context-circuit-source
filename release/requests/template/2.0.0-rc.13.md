# Context Circuit 2.0.0-rc.13

A candidate for 2.0.0-rc.12 with five behavior changes: `check` reads a note's
reviewed date against the code it anchors to, every `check` finding names what
discharges it, a workspace can mount knowledge it does not own, a record
written in another language is composed in that language rather than translated
into it, and a new workspace's README is titled with that workspace's own name. It also rewrites the documentation a workspace is delivered with, which
is the largest change here by volume and the first thing a new workspace shows
anyone. No record changes shape, no existing file moves, and
nothing is converted for you. The v2 description in 2.0.0-rc.1 still stands. This
template recommends CLI `2.0.0-rc.13`. Git is required. No Go or Python runtime
is.

## The reviewed date was write-only

Every catalog entry ends with the date its note was last confirmed against the
code. `check` enforced that the date was there. Nothing ever read it back.

So knowledge went stale invisibly. The one loop that brings a note back for
judgment is completion, which returns the entries scoped to a plan's
repositories — and that only ever fires for work done through this workspace. A
merge by somebody else, a commit from before the workspace existed, a hotfix
pushed straight to the branch: none of them reach it. The note sits there reading
confidently and wrong, and the date beside it says nothing, because nobody was
comparing it to anything.

`check` now compares it — to the code the note itself points at:

```yaml
issues:
  - issue: "context/INDEX.md:7: domains/invoice-lifecycle.md was last confirmed 2026-06-01,
      and api@internal/billing/dunning/ has 2 commits since"
    resolve: "needs a person: read the note against the code it anchors to, then edit the note
      and its catalog entry together and move the reviewed date — or move the date alone if
      nothing it says changed"
```

### Against the code, not against the calendar

The obvious design is a threshold — report anything older than N days. It is not
what this does, and the reason is worth writing down.

Age is not evidence. A note whose anchors nobody has touched is not stale however
old its date is, and a calendar threshold reports it anyway. Worse, it produces a
list that never reaches zero: on a workspace of forty notes, some are always past
any threshold, so the findings become something to scroll past — and they would
be scrolled past in the same output as every other finding this candidate just
taught to name its own remedy.

The evidence was already there. A note's anchors are collected in an `Owner:`
block by rule, written as `api@internal/billing/dunning/`, and the readability
pass has parsed that shape since 2.0.0-rc.11. Resolving the repository ID through
this machine's binding and asking Git what changed under those paths since the
reviewed date turns a birthday into a claim with a number attached.

Two deliberate quiet cases. Commits dated the day of the review do not count: a
note confirmed that day was confirmed against them, and counting them would fire
on every note the moment it was written. And a repository this machine has not
obtained reports nothing here, because it already has a finding of its own and
burying that one under every note anchored into it helps nobody.

### The one case age is all there is

A note that anchors to no code — an external contract in `references/`, a
`product/` note about why something exists — has no evidence to read. Nothing in
the workspace will ever bring it back on its own.

For those, and only those, calendar age applies, and only where a workspace asks
for it:

```yaml
knowledge_review_days: 180
```

Unset, they are silent. It is shared rather than local, because how long a fact
may go unconfirmed is a project judgment and not one machine's.

## `check` reported the fault and left the remedy to be guessed

Every other command here hands back the next move. `record approve` returns
`planning_required`. `record complete` returns `reconcile_required` with the
entries to judge. `worktree prepare` refuses a dependent plan and names the
branch to pass. `help` is documented to say what a command decides, refuses, and
leaves to the caller.

`check` was the exception. It returned a list of strings —
`worktree association needs attention: .worktrees/p0001/api`,
`record ID missing from permanent ledger: p0003` — and stopped. Each stated a
diagnosis and none stated a resolution, so the caller derived one. For an agent
that means improvising, in the one situation where the workspace is already
inconsistent and improvising is most expensive: one plausible inference from
"worktree association needs attention" is `worktree remove --discard`, which
throws away somebody's uncommitted work. The docs already warned against adding
`--discard` "merely to bypass a failure" — the warning existed because the
provocation did.

A finding now carries both halves:

```yaml
issues:
  - issue: knowledge repository core-service-knowledge is not obtained on this machine
    resolve: "`knowledge clone --id core-service-knowledge`, which needs no --url because the workspace already describes it"
  - issue: "duplicate record ID: p0003"
    resolve: "needs a person: two clones allocated the same number; renumber one record
      and every reference to it before either is shared, and keep both reservations"
ok: false
```

`resolve` is an instruction rather than a category. It names the command where
one exists, names the edit where an edit is the whole of it, and opens with
`needs a person` where neither is true.

That third kind is the underrated half. Before this, a finding a person must
settle looked identical to one a command fixes — both were strings in the same
array — so an agent had no way to tell "select a member" from "two clones
allocated the same ID". Saying so explicitly converts *no resolution named, so
guess* into *no mechanical fix exists, so stop and ask*, which matters in a
product whose whole shape is about what an agent may not decide alone.

Writing them was a pass over every way a workspace can be wrong, asking for each
whether a command discharges it or a person must. That list did not exist
anywhere before, and it is now the diagnostic itself rather than a document
beside it.

## The knowledge a workspace does not own

`context/` assumes the workspace owns what it describes. That assumption is built
into the loop that keeps it true: completing a plan returns the catalog entries
scoped to that plan's repositories, and the note and its entry move together.
Work done here is what makes a note here wrong, so work done here is what brings
it back for judgment.

An organization's knowledge center breaks every part of that. One repository is
read by many workspaces, it is changed by teams that do not work in any of them,
and no plan completed here will ever invalidate it. It was still knowledge the
agent had to read — how the file service signs an upload, which notification
channels actually exist, what the deployment proxy does — and the product had
nowhere to put it.

So a workspace with one had two moves, and both were bad. Copy the notes into
`context/`, where a duplicate goes stale silently while still reading as current
and nothing in the workspace can tell that it has. Or leave them out, and watch
each agent re-derive facts somebody already wrote down, from source, from
Swagger, from trial and error.

It is mounted instead:

```yaml
# workspace.yaml — shared
knowledge_repositories:
  core-service-knowledge:
    url: git@git.example.com:platform/core-service-knowledge.git
    default_branch: main
    index: index.md
```

```yaml
# repositories.local.yaml — this machine
knowledge:
  core-service-knowledge:
    path: repositories/core-service-knowledge
```

The split is the one every checkout already makes. Where it lives, which branch
everyone reads, and which file maps it are facts the whole team shares; the
checkout path describes one machine. `knowledge clone` puts it under
`repositories/<id>`, beside the working copies and already excluded by the
shipped `.gitignore`, and takes no `--url` for an ID the workspace already
describes — which is what joining a workspace that has one looks like.

### A separate record, not a separate directory

It is not an entry in the `repositories` map, for the reason
`workspace_repository` is not, and that map has now refused two different things
for it. Every consumer of it reads an entry as somewhere work happens: a plan
names repositories, a relationship joins two, a worktree is cut from one, and
`record order` derives waves across them. None of those is ever what a knowledge
repository means. It records no base branch, because work never starts in it.

The checkout is another matter, and it lands in `repositories/` with the rest.
What separates knowledge from work is the record, not the directory, and a
directory of its own would only assert a separation the record already makes —
while adding a second place to look for a checkout and a second line to ignore.

The two maps do share one ID namespace. A note's anchor names a repository by ID
— `api@internal/billing/dunning/` — so an ID meaning two things makes every
anchor carrying it ambiguous. That is also what makes one directory safe: no
knowledge ID can collide with a repository's, so no checkout can collide either.
Connecting an ID the other side already holds is refused in both directions, and
so is mounting a checkout that is already bound as a repository where work
happens.

### Read-only is enforced, not requested

Obtaining one disables its push URL, and every sync reasserts that, so a checkout
obtained before this existed and one whose push URL was restored by hand both end
up read-only again. A push fails against `READ-ONLY-KNOWLEDGE-REPOSITORY` rather
than half-succeeding, and Git echoes that back, so the refusal explains itself at
the moment someone tries rather than in documentation they did not read.

This is deliberate, and it is the one place in this product where a rule is
mechanical rather than written. Almost every other boundary here is conditional —
read the exact source files the task names, commit here but not there — and a
condition cannot be a Git setting. "Never write to a repository this workspace
does not own" has no conditions in it, so it does not need an agent to remember
it.

An improvement goes upstream through that repository's own review, from a
separate checkout of it. That is slower than editing in place, and it is the
point: an edit that lands only here helps nobody and is lost on the next
fast-forward.

### Sync fetches, then fast-forwards only when it is safe

`knowledge sync` fetches, then fast-forwards to the shared branch — and only when
the checkout is clean and on it. It never merges, rebases, resets, or discards.

A checkout holding uncommitted work is reported and left exactly as it is. A
checkout holding commits, where the upstream has also moved, is reported as
diverged and left exactly as it is. Both say plainly that nothing was changed,
and both name where the work should go instead. Moving somebody's work is not a
decision this command has standing to make, and a sync that quietly resolved it
would be indistinguishable from a sync that ate it.

### Retrieval reads both, and says which is which

`context find --query` now searches this workspace's catalog and every mounted
index, and marks each match with the source it came from and whether it is
borrowed. That mark is the whole difference between an entry to edit and one to
raise upstream.

It also reports any index it could not read, rather than returning a shorter
list. A borrowed index this machine has not obtained would otherwise narrow the
result in silence, and a search that found nothing reads identically to one that
never looked — which is the confident miss the catalog exists to prevent.

A borrowed repository writes its index its own way. Matching stays plain
case-insensitive substring over whole lines, so an index in some other project's
format is searched as it is rather than parsed as this product's catalog and
found empty.

### What `check` says, and what it deliberately does not

`check` reports what stands between this machine and reading the knowledge: a
repository nobody here has obtained, naming the command that obtains it; a
checkout with local edits in a repository that is read-only here; one sitting on
a branch nobody else reads; one behind its remote as of the last fetch; and a
recorded index that cannot be read, or was never recorded at all.

It reports nothing about the content. The catalog rules — one note one entry, a
reviewed date, anchors in an `Owner:` block, a heading that says what belongs
under it — exist so that a person here can fix what they break. Neither half is
true of a repository this workspace does not own, and a diagnostic that reported
faults nobody may correct would stop being worth reading.

For the same reason, completion never names a borrowed entry as knowledge to
reconcile. `reconcile_required` is an obligation, and an obligation nobody here
can discharge is noise. Borrowed knowledge goes stale on its owner's schedule;
when you find it wrong, say so and raise it upstream.

## A record in another language was English wearing other words

2.0.0-rc.12 decided which language a record is written in. It decided nothing
about how that language is written, and the gap showed in the first Indonesian
intents: grammatical, precise, and stiff — English sentences with Indonesian
vocabulary.

The symptoms were consistent. English clause architecture survived the crossing,
so a sentence hinging on `, so` stayed one sentence where Indonesian would use
two. Nominalizations came across intact — "no change to how the current quarter
is determined" is ordinary English and heavy almost everywhere else. Technical
vocabulary was translated inconsistently, keeping `cache` and `backend` while
rendering `refresh` as `penyegaran`. And the register drifted without anyone
choosing to move it: words that are neutral in English land as bureaucratic when
carried across literally, so plain English became formal Indonesian.

Underneath all four, the product prescribed *how to write* only for English.
`cc-knowledge` carries a style section whose thresholds 2.0.0-rc.12 admitted were
"calibrated by measuring an English tree", and everything else reached another
language through a translation step nobody had described.

### The structure is English whatever the prose is

`Goal`, `Non-goals`, `Constraints`, `Success criteria`, `Repository scope`, and
`Open questions` are the record's shape, not its content — the same category as
`created_by`, the slug, and the dates, all of which the language table already
pins as unchanged. They were being translated because nothing said they were
structure.

Three costs. Two members produce differently-shaped records, so a reader no
longer knows where to look. The translation itself drifts — `Bukan tujuan` in one
session, `Di luar cakupan` in the next — and a field name that varies per
generation is not a field name. And nothing can find them: nothing parses
headings today, but the catalog already learned this exact lesson, and is English
because substring search over a mixed-language index quietly breaks.

The language table gains the row, and the entry instruction says why.

### Compose in the language rather than into it

`cc-intent` carries the procedure, and `cc-plan` the short form: let sentence
structure follow the target language rather than preserving English clause order
and length, prefer the verb where English would nominalize, and keep technical
vocabulary in the form engineers in that language actually say — consistently,
because half-translated technical prose reads worse than either choice made
whole.

Each rule names an operation rather than a virtue, because "write naturally"
gives a model nothing to apply while "split a sentence that keeps an English
hinge" does.

The skill carries no worked examples, and that is a deliberate limit rather than
an omission. An example is necessarily in one language, and `cc-intent` loads for
every member whatever they write in; three Indonesian pairs are guidance to one
team and noise to the next, with a real risk of anchoring an agent on conventions
that belong to a language it is not writing. A team that wants specifics records
a `tone` instead, which is the mechanism for exactly that and reaches only the
members it describes.

### A team can say what register it wants

A member may record one beside their language:

```yaml
members:
  kao:
    name: Kao
    language: Bahasa Indonesia
    tone: semi-formal; keep technical terms in English
```

One line of prose, quoted into the instruction that writes a record rather than
parsed — recorded exactly as `language` is, and for the reason that field gives:
the only reader is a sentence quoting it, and a tag would need a table that is
wrong for the first register it omits.

It is per member rather than per workspace because a register is meaningless
without the language it applies to, and the language is already per member.
Unset leaves the general guidance to decide, which is what every record written
before this assumed. The product ships no register default for any language:
Context Circuit cannot have a considered opinion about every language, and two
teams writing the same one will want different answers.

## The workspace no longer arrives undocumented

The README a workspace is created with described the CLI. That was the wrong
audience for the first file anyone opens: a person arriving at a new workspace
needs to know what the thing does for them and how to start, not the command
surface, which `.context-circuit/docs/commands.md` already carries for the agent.

It is rewritten around what a person actually does — a quick start that ends with
a working workspace, the conversations that drive a change through approval,
execution, delivery, and completion, and the stacked-plan behavior that is hard to
believe without seeing it drawn. The plan diagrams are Mermaid, so they are
readable in the file and correctable in review rather than being pictures nobody
can edit.

`.context-circuit/docs/how-it-works.md` is new, and it is the first shipped
document written for a person rather than for the agent. It follows one request
from the sentence somebody types through to the knowledge that request made
stale, and at each step names what the agent does, what it reads from the
workspace, and what the CLI is asked for. It exists because the division of
labor between person, agent, workspace, worktree, and CLI was only ever stated in
`AGENTS.md`, in the imperative, to an audience that is not the person deciding
whether to adopt this.

`AGENTS.md` does not name it. A doc written for a person spends context an agent
never acts on, and two tellings of the same rules — one normative, one
descriptive — drift apart with the descriptive one reading as though it explained
the authoritative one. The entry instruction still names every document the agent
does need, and a test now enforces the split in both directions.

A workspace also arrives with the artwork its README renders, under
`.context-circuit/assets/readme/`. Only those three images ship: a repository
avatar, a favicon source and a social preview are uploaded to a repository or a
site, and a workspace carrying them would be carrying most of a megabyte it never
renders. What remains is about 1.1MB, carried in the template repository rather
than fetched, so a workspace clone is self-contained and renders offline.

## A new workspace's README says whose workspace it is

The README a workspace is created with is the product guide, and in an installed
workspace it is also that workspace's own front page. Two spans of it were wrong
as shipped: the heading named the product, and the version badges looked up the
newest published release rather than the versions that workspace actually
received.

Initialization now rewrites both. The heading becomes
`Context Circuit - <your workspace name>`, taken from the `--name` already given,
and the badges become static, carrying the template and CLI versions recorded in
`.context-circuit`. A workspace repository is shared with a team, and its front
page should answer whose it is and what it runs without anyone opening a file.

The shipped README delimits both spans with HTML comments so the rewrite has an
exact anchor rather than a guess about where a heading ends. A README whose
markers are gone has been edited by whoever owns that workspace, and is left
exactly as it is — initialization records data, and rewriting somebody's prose to
find a foothold is not a judgment it may make.

## Both products now carry a license

They left this checkout with none, which is not a neutral default: it is the one
answer a legal review cannot act on. There are two, because the two products sit
differently with the people who receive them.

`context-circuit-cli` and this source are **Apache-2.0**. It is a
binary an organization installs across its machines, and the explicit patent grant
is what carries that past a review without a conversation.

Everything a workspace receives is **0BSD**, which permits use, modification and
redistribution with no attribution requirement at all. Those files are copied into
somebody else's repository and edited there, which makes them theirs in every
sense that matters. Any notice-retention clause — MIT's included — would oblige
every workspace to carry a notice of ours inside a repository that is not ours,
forever, as a condition of using a scaffold.

The 0BSD text ships to `.context-circuit/LICENSE`, travelling with the files it
covers. It is deliberately not installed at a workspace root, because GitHub reads
the root `LICENSE` to label a repository, and a workspace root belongs to your
project rather than to this one.

Every CLI archive now carries its own `LICENSE` beside the binary. It shipped the
licenses of its dependencies and the Go runtime and not its own, which Apache-2.0
asks a redistributor to pass on. An archive is read wherever it was downloaded,
where no repository label is there to answer for it — and until this candidate the
label it was served under said 0BSD. The release notes name the license too, and
the archive inventory is asserted by the release check, so this cannot quietly
regress.

The published template repository gains its own license, conduct, contributing and
security pages, which GitHub renders as tabs beside the README. They are held
outside the release manifest for the same reason and reach no workspace.

## One command group is new

```
knowledge connect|clone|sync|remote|list
member tone
```

`member add` takes an optional `--tone`, and `member tone --clear` removes a
recorded one — prose has no sentinel the way `member band --band 0` clears a
band.

`check` returns a different shape: each finding is an object carrying `issue` and
`resolve`, where it was a plain string. It also reports two findings it never did
before, both about knowledge whose date has stopped matching the code. `context find --query` returns a
different shape too: matches carrying a source and a `borrowed` flag, beside the
indexes it could not read. A caller reading either as a flat list of strings
needs updating; `ok` is unchanged, as is the non-zero exit when findings exist.
`context find --repo` is unchanged.
`status` gains a `knowledge_repositories` section when a workspace has any. No
other command changed, and no command commits, pushes, or merges anything.

## The CLI is released from its own repository, tagged `cli-v*`

The CLI is built from
[context-circuit-source](https://github.com/kaotypr/context-circuit-source), and
that repository is now public. Its releases are published there, on the commit
that built them.

They were published here instead, because installing could not depend on reading a
private repository. The cost was a tag that meant two things in two places — a
build reference there, a marker here pointing at a commit containing no Go — a
token with write access across repositories, and Apache-2.0 binaries served from a
repository whose own label says 0BSD. Opening the source removed the reason, so
the release followed the code, and each repository's label now matches the assets
it serves.

The tag is shorter too. Releases were tagged `context-circuit-cli-v<version>`,
which repeated the product's name inside a release list that already carries it;
they are `cli-v<version>` now.

The assets under that tag are unchanged: an archive is still
`context-circuit-cli-v<version>-<os>-<arch>`, because it is read wherever it was
downloaded rather than in a list that supplies the context.

Publication targets GitHub only now, and installation reads it directly. Both
pipelines mirrored every release into a private GitLab project as well, which
was one deployment's arrangement living inside the product's release machinery,
and the `cli_registry` field that pointed a workspace at such a mirror is gone
with it. An organization is still free to mirror either published repository
into its own hosting — that is a copy of a Git repository and asks nothing of
this product — but a workspace initialized from a mirrored template installs its
CLI from the GitHub release like every other workspace. A second install path
bought a version that resolves in one place and not another, and a credential
whose destination depended on a recorded field.

**Take this candidate's `cc-cli` skill before asking for a newer CLI.** An
installer from an earlier candidate resolves the old repository and the old tag,
and will find neither. Both changes are maintainer actions taken now rather than
after 2.0.0, because everything they supersede is a prerelease. Nothing about the
installed binary changes: it is `context-circuit-cli`, from a literal in the build
script that no tag or repository has ever fed.

## Breaking: a workspace recording `cli_registry` does not load

The field is gone from the schema, and `workspace.yaml` rejects a key it does
not know. That is the existing contract rather than a new strictness — it is the
same rule that makes each workspace pin its CLI version — but it means a
workspace that recorded a mirror stops at the first command rather than at the
first install:

```
workspace.yaml: [6:1] unknown field "cli_registry"
   5 | relationships: []
>  6 | cli_registry: "https://gitlab.example.com/acme/context-circuit"
```

Delete the line. Nothing replaces it, nothing else in the file changes, and no
state is lost: the value was read only when installing. The installers drop
`--gitlab-url` and `CONTEXT_CIRCUIT_GITLAB_URL` with it, so a script that passed
either is now refused by name rather than quietly ignored.

## Corrections

Five defects found by reading the tree rather than by using it. Each is a case
where a command did something other than what it was asked:

- An empty command argument crashed. `context-circuit-cli ""` reported the
  unknown command correctly, then went looking for its first word to suggest a
  help topic, and there is no first word.
- `member band` with no `--band` cleared the member's block instead of refusing.
  Zero is the documented way to clear a band, so an omitted flag was
  indistinguishable from a deliberate `--band 0` — and the caller who forgot it
  is the one who cannot have meant it.
- `record create` rendered a created record's body to a person as a YAML scalar,
  which arrives as a single escaped line. The reservation and the path now lead,
  because they are what was asked for, and the body follows as itself — the
  shape `record show` already prints.
- One-shot Git configuration inherited from the environment reached the CLI's
  own Git commands. A host that ran `git -c` exports it to everything
  underneath, so a setting meant for one command applied to the workspace's
  repositories without saying so. `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM`
  are untouched: a person sets those to isolate an environment, and no Git
  operation sets them.
- `install.sh` demanded a value before it read the option name, so `--help` was
  refused, an undefined option was reported as one missing an argument, and a
  bare `--version` said that options in general take values rather than naming
  the one left bare. It now checks the name first and prints usage when asked.
  `install.ps1` gets all three from PowerShell's own parameter binding.

## Record format

Records written by 2.0.0-rc.4 and later are read by this candidate unchanged.
`knowledge_repositories` and the `knowledge` binding are optional: a workspace
from 2.0.0-rc.12 loads without them, and a workspace that never mounts one never
grows either key. A member's `tone` is optional in the same way, and no record
written by an earlier candidate is rewritten — an intent carrying translated
headings keeps them, because rewriting an approved record to match a new
convention is not worth what it costs.

An older CLI cannot read a workspace that has them. Unknown fields in structured
records are errors, which is the existing contract and the reason each workspace
pins its CLI version.

## Upgrading

Install the CLI, then take this release's `AGENTS.md` and the `.agents/skills/`,
`.claude/skills/`, and `.cursor/skills/` trees into the workspace. An `AGENTS.md`
you customized needs merging rather than replacing; the paragraph that changed is
in **Shared knowledge**. No skill directory is new, and no ignore rule changes:
a mounted checkout lands in `repositories/`, which every workspace already
excludes.

The `cc-cli` skill is not optional this time: its installers resolve a different
repository, and an older copy will keep asking the template repository for CLI
releases that are no longer published there.

If your `workspace.yaml` records `cli_registry`, delete that line before running
anything — it is the one edit this release requires, and until it is made every
command refuses the file. See **Breaking** above.

`README.md`, `.context-circuit/docs/`, and `.context-circuit/assets/` are worth
taking too, though nothing depends on it — an existing workspace keeps working
with the README it already has. Take them as a set: the README links the docs and
references the artwork by path, so a partial copy leaves broken links. A README
you have edited is yours; this one is a replacement, not a merge.

Taking that README gives you the product guide, not your workspace's name: the
heading is written at initialization, which for an existing workspace has already
happened. Edit the line between the `context-circuit:title` markers if you want
it, and set the two badge versions to what you pin. Nothing reads either.

`.context-circuit/LICENSE` is new and worth taking with them. Nothing depends on
it; it is there so the terms covering those files travel with the files.

`check` needs nothing done to it, but it will report more than it did before:
every note whose anchors have moved since its reviewed date, which on a workspace
that has been running a while is most of them at once. That backlog is real
rather than a false alarm, and working through it is ordinary knowledge
maintenance — but expect the first run after upgrading to be long, and do not
read its length as a fault in the release. `knowledge_review_days` stays unset
unless you set it. Nothing else is required. A workspace with no
knowledge center to mount does nothing differently, and no existing file changes until someone runs a `knowledge`
command.

To mount one:

```sh
context-circuit-cli --workspace <root> knowledge clone --id core-service-knowledge --url GIT_URL
```

On another machine, clone or connect the same ID and pass no URL. `agent setup`
is not required by this release: no role definition changed, and a worker never
reads borrowed knowledge or writes a record, because it works inside a
repository worktree under that repository's instructions.

Nothing needs setting for tone either. A team happy with the general guidance
records nothing; a team that knows the register it wants says so once:

```sh
context-circuit-cli --workspace <root> member tone --id ID --tone 'semi-formal; keep technical terms in English'
```

## Candidate status

Deterministic tests cover the mount end to end. Obtaining one lands at the
default path, writes the shared record with its detected index, writes the
binding to the local file, disables the push URL, and an actual `git push`
against it fails. Retrieval returns a borrowed match carrying its source and
flag. A borrowed entry naming a repository in this workspace's own `{api}` form
is asserted *not* to appear among the entries offered for reconciliation, which
is the case where the two knowledge layers are easiest to confuse.

Sync is covered in four states with the files checked afterwards: current, a real
fast-forward that brings the upstream change in, a dirty checkout that reports
and keeps the uncommitted file, and a diverged checkout that reports and keeps
the local commit. The ID namespace is covered in both directions, plus mounting a
checkout already bound as a repository. `check` is covered for the missing
checkout, asserting the finding names the command that fixes it.

The review pass is covered where it matters most — that it stays quiet. A note
whose anchors nobody touched reports nothing however old its date is; a commit
dated the day of the review reports nothing; a repository this machine has not
obtained reports nothing, and the binding finding is asserted present instead.
Code moving under an anchor is asserted to report the note, the date, the anchor
and the commit count, with a commit elsewhere in the same repository asserted not
to change it. The unanchored fallback is covered in both states, silent without
`knowledge_review_days` and reporting with it.

Findings are covered by an invariant rather than one by one: a workspace is put
into several unrelated faulty states at once — two unbanded members, an
unobtained knowledge repository, an unreserved plan linked to nothing, an
uncatalogued note beside an entry pointing nowhere, an undescribed workspace
repository — and every finding it produces is asserted to carry a non-empty
resolution. Six are then asserted to name the specific thing that discharges
them, including one `needs a person`. A clean workspace is asserted to still
report nothing and exit zero, which is what makes the rest worth reading.

The README rewrite is covered in both directions. A workspace initialized under a
name is asserted to carry that name in its heading and the versions it received in
its badges, with the release lookups asserted gone; a name containing markup is
asserted escaped rather than trusted; and the shipped README is asserted to carry
exactly one of each marker, so losing one fails here instead of silently shipping
workspaces titled with the product's own name.

The two licenses are asserted separate: the Apache text at the root, the 0BSD text
in the shipped tree with no Apache anywhere in it, and the manifest asserted to
install it under `.context-circuit/` and never at a workspace root. Publication is
covered for the landing-page files — they appear in the published repository, the
license there is byte-identical to the one a workspace receives, an exported
workspace is asserted to carry none of them at its root, and a `README.md` among
them is refused rather than quietly replacing the product guide.

For tone, the mechanical half is covered: the register round-trips into
`members.yaml` and back out of `member list`, `member add` carries it, `--clear`
removes it and leaves the language alone, and it is refused when it stops being
one usable line — empty without `--clear`, both flags at once, an unknown
member, several lines, an essay. The structure rule is asserted present in the
entry instruction by name, and both record-writing skills are asserted to carry
the composition rules, with `cc-intent` asserted to carry the contrastive
examples rather than the rule alone.

What no test here establishes is the premise. Nothing measures whether an agent
actually reads a mounted knowledge center before re-deriving a fact from source —
that is the failure this exists to prevent, it is reported rather than observed,
and it rests on an instruction being followed. Nothing measures whether an agent
refrains from copying a borrowed note into `context/`; the copy is prohibited in
the entry instruction and in `cc-knowledge`, and unlike the write, it is not
mechanically prevented, because a file written into `context/` is an ordinary
file write.

What the review pass cannot see is a note made wrong by a change that touched
none of its anchors — a renamed concept, a decision reversed elsewhere, a
dependency upgraded under it. Anchors are a proxy for what a note describes, and
a good one, but a note is reported because code it points at moved and not
because the note became untrue. The two overlap; they are not the same set, and
nothing here closes that gap.

Whether any of the tone guidance changes what a model writes is not measured and
cannot be measured here. It is a claim about prose quality in a language this
product's tests do not read, resting on an instruction being followed — and more
weakly than the language rule it sits beside, because a register is softer than
a rule, and because the guidance is deliberately general where a worked example
would have been specific. What a green suite establishes is that the field
arrives where the writing happens, not that the writing improved. This candidate
leans on the model's own command of the language; read the next record and judge
it.

The documentation is unverified in the only way that matters. Its commands are
executed against a fixture by the suite, and its diagrams render, but no one has
watched a person who does not already know this product try to start a workspace
from it. The claim that it explains the thing is a claim about writing, and this
candidate is where you find out.

The mount has been exercised only against fixture repositories, not against a
real knowledge center of any size. Retrieval reads one index file per mounted
repository; a knowledge center whose index does not list everything, or whose
entry point is a directory rather than a file, is not served by this and will
report an index it cannot read. Exercise the flows you rely on before depending
on this release.
