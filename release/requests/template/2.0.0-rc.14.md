# Context Circuit 2.0.0-rc.14

A workspace is somebody else's repository. Until this release it arrived
carrying this product's front page: a README about Context Circuit, the artwork
that README renders, and a license file. A project that adopted a workspace got
a repository whose first screen described the tool rather than the project, and
whose GitHub label said 0BSD because a `LICENSE` sat at its root.

That was never the intent — three of the landing-page files were already held
back for exactly this reason — but the README and the license were not, and the
delivery path most people use made it worse than it looked.

## What a workspace receives, and what it no longer does

Gone from a workspace: `README.md` as shipped, `.context-circuit/LICENSE`, and
`.context-circuit/assets/readme/`. The published repository keeps all three, at
its own root, where they describe the repository a visitor is actually looking
at.

The license is not lost, it is placed. 0BSD asks nothing of the project the
scaffolding is copied into, so a copy inside every workspace answered a question
nobody had while adding a file the workspace had to explain. The terms still
govern everything a workspace receives; they are stated once, at the root of the
repository that is the template.

## The front page is written for the project

Initialization now writes `README.md` rather than retitling a guide that
shipped. It carries the workspace name, what that workspace is for, and the two
versions it actually received:

```
Context Circuit - Acme Billing

  workspace v2.0.0-rc.14   cli v2.0.0-rc.14

  Ship the new invoicing flow across the API and the web client
```

Below that: what the repository is, what Context Circuit is, a table of where to
look, and a closing line saying the file belongs to the project now.

The purpose is new. It comes from `--purpose` at initialization and renders
between markers, so a workspace whose purpose changes can have that line
regenerated without the rest being touched.

A directory that already has a `README.md` keeps it. Initialization no longer
refuses over one either: a project adopting a workspace usually has a front page
already, and having one is not a reason to stop. If the file still carries the
generated markers, the spans inside them are refreshed and nothing else is; if
it does not, the file is left exactly as it is.

## Why `git archive` decides this

A workspace is created from a published tag, and the tool people use for that
extracts the tag with `git archive`. The published repository now commits a
`.gitattributes` marking every path it owns `export-ignore`:

```
README.md  LICENSE  CHANGELOG.md
CODE_OF_CONDUCT.md  CONTRIBUTING.md  SECURITY.md  assets/
```

Those files stay in the tree, so the repository still renders its guide, its
artwork and its license tab. They leave the archive, so a new workspace never
sees them. One tree, two audiences, and git decides which is which rather than a
convention nobody can check.

## A template update is told not to write them back

A later template version is applied by diffing the recorded tag against the
newer one. A diff reads the tree, where these files are present, and cannot see
`export-ignore` — so the mechanism that protects a new workspace does nothing
for an existing one.

`AGENTS.md` now carries an **Updating the workspace template** section naming
the same paths and stating the rule directly: a delta that touches them is read,
not applied; do not create one, and do not update one that exists. Everything
else stays ordinary which-side judgment, and the two version stamps take the
template's value because they record what this workspace received.

This is the half that depends on an agent following an instruction rather than
on a tool enforcing one. It is written where the agent already reads.

## Upgrading

Nothing is required of an existing workspace, and nothing in it stops working.

A workspace created before this release still holds `README.md` as the product
guide and `.context-circuit/LICENSE`. Both are yours to keep or delete. Deleting
the license changes nothing about the terms; 0BSD does not ask to be carried.
Replacing the README with a page about your own project is what a new workspace
now gets by default, and there is no command that does it for you — this release
does not rewrite a front page somebody may have already edited.

The `.context-circuit/assets/readme/` images are referenced only by the shipped
guide. If you replace that README, they can go with it.

## Candidate status

A release candidate for the v2 layer. Records written by 2.0.0-rc.4 and later
are read unchanged, and this release changes no record format. What changed is
the file inventory a workspace receives, which the CLI's own release records in
more detail.
