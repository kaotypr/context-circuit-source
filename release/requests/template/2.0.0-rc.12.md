# Context Circuit 2.0.0-rc.12

A candidate for 2.0.0-rc.11, drawn from using it. No record changes shape and
nothing is converted for you. The v2 description in 2.0.0-rc.1 still stands. This
template recommends CLI `2.0.0-rc.12`. Git is required. No Go or Python runtime
is.

Three findings from use, plus one diagnostic that had been waiting for a second
member to make it matter.

## The workspace could not describe its own repository

Every shared record — intents, plans, the ID ledger, the knowledge tree — travels
through the Git repository carrying the workspace. A member therefore reads plans
from whatever commit their workspace checkout happens to be sitting on. Nothing
reported that: `status` and `check` walked the repositories map, and the
workspace was not in it.

It was *possible* to register it. `repo connect --path .` worked, and the `repo`
help said so. But that put the workspace into a map every consumer reads as
somewhere work happens: a plan names repositories, a relationship joins two, and
a worktree is cut from one. A worktree of the workspace duplicates the records
the CLI is reading, and nothing refused it.

So it is described beside that map instead:

```yaml
# workspace.yaml — shared
workspace_repository:
  url: git@github.com:acme/acme-workspace.git
  default_branch: main
```

```yaml
# repositories.local.yaml — this machine
workspace:
  path: .
  base_branch: main
```

The split is the one every repository already makes, for the same reason. Where
it lives and what it defaults to are facts everyone agrees on; the checkout root
and the branch this machine works from describe one machine. `workspace connect`
writes both, reading the URL from the checkout's `origin` unless `--url` gives
one. `workspace base` and `workspace remote` change the local and shared halves
afterwards, as `repo base` and `repo remote` do.

`--path` defaults to the workspace root and needs naming only when the workspace
sits inside a larger repository, where it names the containing root. That is why
the binding carries a path at all.

Once described, `status` reports the workspace's own branch, base branch, and
uncommitted records beside every repository's, and `check` stops asking for it.

`repo connect` now refuses the workspace's own checkout and names
`workspace connect` instead. A workspace that already registered itself that way
keeps working; only new connects are refused.

### Why members do not each get a workspace branch

The obvious next step is a branch per member, recorded in `members.yaml`. It is
not in this candidate, and the reasoning is written down so it does not get
relitigated from scratch.

A member has no long-lived stream of workspace work — they have episodic edits:
create an intent, approve it, create plans, complete them. A long-lived branch
for that drifts and becomes a merge burden buying nothing.

Worse, it would quietly make allocation bands mandatory. The ID ledger records
permanent reservations; a reservation sitting on an unmerged branch is invisible
to everyone else, so two members can each believe they reserved the same number.
Bands make that safe only if every member holds a distinct one. And `record
order` derives waves by reading plans — on a divergent branch it orders against a
partial set and emits wrong waves confidently.

It would also repeat a mistake this product already corrected once. In
2.0.0-rc.6, `base_branch` moved out of the shared record precisely because one
value there described every machine at once. A per-member branch in a shared file
is that shape again.

Members share one branch of the workspace. A machine that works from another
records it in the local binding, where it describes that machine and nobody else.

## A diagram fenced under its own type

An agent writing knowledge produced this:

    ```stateDiagram-v2
    [*] --> Drafted
    ```

instead of a `mermaid` fence with `stateDiagram-v2` on its first line. The fence
names the language; the first line inside it names the diagram type. Opened the
other way it renders as plain text in every reader, and it passed `check`
completely — the diagram-type validation only ever ran *inside* a correctly
opened fence, so this looked like an ordinary code block and was ignored.

It is the worst kind of formatting error: deliberate-looking in the source,
blank in the reader, and therefore survives review.

`check` now reports a fence opened with any recognized diagram type, naming both
the type and the fix. `cc-knowledge` and the shipped `context/INDEX.md` show the
correct fence rather than only naming the diagram types, which is the part that
prevents it rather than catching it afterwards.

## Unbanded members in a shared workspace

`check` reports members allocating from the shared range once a workspace has
more than one. Bands are what let clones that cannot see each other allocate
without colliding; a solo workspace needs none, so the finding waits until a
second member makes a collision possible rather than nagging every workspace
from the day it is created.

## Joining a workspace took a briefing

Describing the workspace repository exposed the flow around it. A member who
cloned an active workspace had to be told, step by step, what to do — and one of
those steps was a workaround.

`repo clone` refused an ID the workspace already described: "repository ID is
already registered; connect its checkout instead". But obtaining checkouts of
repositories the workspace already describes *is* what joining one means, so the
single command whose name says "get me this repository" was the one command that
could not. The joining member had to `git clone` by hand and then `repo connect`.

`repo clone` now binds an already-described ID. It takes no `--url` there — the
shared record carries it — and rewrites nothing shared. Passing a `--url` that
disagrees with the record is still refused, and `repo init` is still refused for
such an ID, because an ID already naming a repository is not one to start empty.
An ID nobody describes still needs a `--url`.

The default checkout location was also only ever implied, appearing inside
examples and nowhere as a statement. `repositories/<id>` is now written down as
where working copies belong, in the docs and in `cc-workspace`, which carries the
join sequence as a named section instead of leaving it to be assembled from
scattered sentences.

What this is worth is measured in what a member has to say. Before, joining took
a seven-step briefing that named a workaround. After, the shipped instruction
carries the flow and the request is ordinary:

> Set up this workspace for me, add me as a member, and clone every repository
> it tracks.

## A team that does not work in English

A team talks to its agents in whatever language it talks in, and until now the
product had no position on where that language may end up. It had two accidental
ones instead: a note in the knowledge tree already said an outcome in the
project's own language is the only form a person can meaningfully approve, and
the readability diagnostic already required English, because the actor-story
check matches `**As a ...**` and the sentence threshold was calibrated by
measuring an English tree.

What gets written down now follows the artifact rather than the conversation.

| What is written | In what language |
| --- | --- |
| An intent or a plan | its author's recorded language, English where none is |
| An approval or completion note | exactly what the person said |
| `context/` notes, the catalog, the glossary | English, always |
| Anything written inside a repository | that repository's convention, English where it states none |
| IDs, slugs, repository IDs, branch names, dates | unchanged |

Slugs are the part that does not bend. A record's slug stays a lowercase ASCII
slug whatever its title says, so `tambah-penagihan` is fine and a title in a
script without ASCII is transliterated rather than refused at a validation error
nobody can read from the message.

A member records their language in `members.yaml` beside their name and band,
as a person says it — `Bahasa Indonesia`, not a tag — because the only thing
that reads it is a brief quoting it into a sentence, and a tag would need a
table that is wrong for the first language it omits.

Knowledge does not follow the member. A note outlives whoever wrote it, anchors
to code, and is found by substring search that a mixed-language catalog quietly
breaks. An approval note does not follow either: it is evidence of what a person
said, so translating it falsifies the record rather than formatting it.

## The boundary lives in the brief

A record is quoted whole into the brief a worker receives, fenced and labelled
authoritative. A record in one language therefore invites a worker to answer it
in that language.

The worker never reads the workspace's instructions. It works inside a
repository worktree, under that repository's, so a rule written into `AGENTS.md`
reaches the coordinator and nobody else. `agent dispatch` now names the record
author's language and states the boundary in the brief itself:

> The work described here is stated in Bahasa Indonesia. Write everything you
> put into the repository in English — code, comments, identifiers, tests,
> commit messages — unless this repository's own instructions say otherwise.
>
> Names are quoted, never translated, in either direction. Domain vocabulary
> keeps the form used here, and code identifiers keep the form the code uses.
> Translating either breaks the thing it names.

It names the language rather than stating a general rule, because a specific
sentence holds where a generic one slides, and it appears in every brief,
because a rule that is present only sometimes is one that is missing sometimes.

The failure worth preventing is not a Bahasa comment — review catches that. It
is a domain term rendered into English in an identifier: a worker reads `resi`
in the plan, dutifully writes English code, and names the field
`receiptNumber`. The schema and the glossary now disagree about what the thing
is called, and nothing reports it.

## One command group is new

```
workspace connect|base|remote
member language
```

`repo clone` accepts an already-described ID and treats `--url` as optional, and
`member add` takes an optional `--language`. No other command changed. No command commits, pushes, or merges the workspace, and
the new group does not either.

## Record format

Records written by 2.0.0-rc.4 and later are read by this candidate unchanged, and
2.0.0 will read them too. A workspace still on 2.0.0-rc.3 or earlier is not
converted and starts fresh.

`workspace_repository` and the `workspace` binding are optional. A workspace from
2.0.0-rc.11 loads without them and keeps working; `check` reports the missing
description only when the workspace is actually a Git checkout, because a
workspace nobody shares has nothing to describe.

An older CLI cannot read a workspace that has them: unknown fields in structured
records are errors, which is the existing contract and the reason the version is
pinned.

## Upgrading

Install the CLI, then take this release's `AGENTS.md` and the `.agents/skills/`,
`.claude/skills/`, and `.cursor/skills/` trees into the workspace. An `AGENTS.md`
you customized needs merging rather than replacing. No skill directory is new.

Run `workspace connect --base BRANCH` once per machine on a workspace kept in
Git. On the first machine it records both halves; on a clone it records that
machine's binding.

A workspace that registered itself through `repo connect` still works. Moving it
across means removing that entry and running `workspace connect`; until then the
workspace stays in a map whose other consumers will offer it as a plan target.

`context/INDEX.md` changed, and a workspace that already has one keeps it: take
the mermaid fence guidance into your own catalog by hand, or leave it and read
the shape rules in `cc-knowledge` instead.

Nothing about joining needs redoing. A member who joined an earlier candidate by
cloning repositories by hand has the same bindings the new path produces.

Running `check` after upgrading may report mislabelled diagram fences in notes
gathered by earlier candidates. That is the point of them, and nothing breaks
while they stand.

Nothing needs setting for language. Every member without one writes English,
which is what every record written before this candidate assumed, and a team
working in English never touches it.

`agent setup` is not required by this release. No role definition changed. The
brief grew a `# Language` section, which arrives with the CLI rather than with
any file in the workspace.

## Candidate status

Deterministic tests cover the workspace repository end to end: that `check` stays
quiet until the workspace is a Git checkout, that connecting writes the shared
and local halves to the right files, that a base branch never reaches the shared
record, that `repo connect` refuses the workspace's own checkout and names the
replacement, and that `status` reports the branch and base. The band finding is
covered in both directions. The fence finding is covered for a correct `mermaid`
fence, a fence opened with a diagram type, a flowchart opened with its direction,
and an ordinary language fence that must stay untouched. Cloning a described
repository is covered for the shared record staying byte-identical, for an
undescribed ID still requiring a source, and for `repo init` still refusing a
described one.

The join is a deterministic test, not a walkthrough: it publishes a workspace,
clones it over a bare remote, asserts the diagnostic names each missing piece,
then runs the arrival — roster, member selection, workspace binding, `repo
clone` with no URL, role definitions — and asserts a clean `check`, the obtained
checkout, the written role definitions, and `members.yaml` as the only shared
file touched.

That a brief draws the language boundary is tested: an unset language reports
English, a recorded one is named, the language reported is the record author's
rather than the dispatcher's, and the value is refused when it stops being a
language's name.

Whether a worker obeys the boundary is not tested and cannot be. No recorded
session produced a repository artifact from a record in another language, so the
whole of the language claim rests on an instruction being followed.

The reasoning against per-member workspace branches is argued, not measured. No
team workspace has been run with divergent workspace branches to demonstrate the
stale-ledger and wrong-wave failures; they follow from how reservations and
ordering read the tree, and they are recorded here so the decision can be
reopened against evidence rather than re-argued from memory.

**What no test establishes is whether an agent follows any of this.** The join
test drives the commands directly. Whether an agent derives them from
`cc-workspace` when a member asks in one sentence, whether it describes the
workspace repository unprompted, and whether it writes a correct mermaid fence
rather than relying on `check` to catch it, are claims a deterministic test
cannot make. No recorded session on any host exercised them. Exercise the flows
you rely on before depending on this release.
