# Context Circuit 2.0.0-rc.10

A candidate for 2.0.0-rc.9, drawn from a recorded session rather than from
review. No record changes shape, no configuration file moves, and nothing is
converted for you. The v2 description in 2.0.0-rc.1 still stands. This template
recommends CLI `2.0.0-rc.10`. Git is required. No Go or Python runtime is.

Everything here answers something that actually happened in one workspace
running 2.0.0-rc.9 through eight plans and four releases.

## What the session showed

Three failures, in the order they cost the most.

**An interactive test was reported that could not have been run.** Asked to try a
published CLI, the session ran it as a subprocess and reported pressing Escape,
the rows it cleared, and the exit status. The next message was a screenshot of
the behaviour still broken. The bug it had just certified fixed became the next
intent.

**A worktree was cut from a base branch two commits behind its remote.** Nothing
said so. It surfaced when the person noticed, and recovery cost a stash, a
conflict in their own uncommitted documentation, and a rebase.

**A plan was prepared beside another plan's committed-but-unmerged work and
shipped without it.** The pull request contained a version bump and none of the
fix it was releasing. The refusal 2.0.0-rc.9 added for exactly this is armed by
`depends_on`, and nobody had passed it.

## The instruction now says what may be claimed

The gates govern what may be *done*. Nothing governed what may be *said*, so a
report of an observation never made passed through unchallenged and every
decision after it rested on the report.

> Report what was actually run and what it actually returned. A check you did not
> run is not a check, and an interactive flow you could not drive is not an
> observation: say it is unverified rather than describing what it would have
> shown. Unverified is a complete answer.

This is resident, and asserted resident, because nothing loads a
do-not-fabricate skill before fabricating. It borrows the planner's shape:
unverified, like not-feasible, is a complete answer rather than an admission to
avoid.

## Three commands say what they knew and did not report

None of these refuses. Each adds a field.

`worktree prepare` reports a base branch behind its remote, naming the count,
the counterpart, and what to do about a worktree that already exists.

`record create` reports allocating in a workspace behind its remote. Allocation
bands separate two members; nothing separates one member from their own
unsynchronized clone, and the ledger that would show the collision is the file
that was not pulled.

`record create` and `worktree prepare` both report plan work the starting point
does not contain. Containment decides it rather than completion, because the two
disagree in both directions — a plan can be completed and never merged, or
merged while still open — and containment is what a worktree actually reflects.

The report at creation is the one that matters: that is where declaring the
dependency is still free, the repositories are known, and nothing has been
prepared from anything yet. Declare it there and 2.0.0-rc.9's refusal fires
correctly later. The report at preparation is the backstop for when nobody did.

One sibling is given its branch. Several are not. The correct start is then a
base plus integration merges, which `record order` derives from `depends_on` and
cannot derive from none — so naming one branch would quietly exclude the rest,
and pointing at `record order` would answer with the base that is being
questioned. The several case names the declaration that makes ordering possible
instead.

**None of these fetches.** Each compares against what the checkout already knows,
because a check that reached the network would make every caller wait on it and
fail where there is none. A branch with no fetched counterpart reports nothing
rather than claiming to be current, and silence here is not a guarantee that you
are. A current base, a repository without a remote, a workspace outside Git, a
declared dependency, an explicit `--start`, and work already in the base all stay
silent too: a field that fires when nothing is wrong is one its reader learns to
skip.

## Work is grounded in the repository it happens in

A prepared worktree is a checkout with its own `AGENTS.md` or `CLAUDE.md` and
possibly its own skills, and nothing told the agent to read any of it. The entry
instruction and the worker brief now do, matching repository skills on their
descriptions rather than their bodies, and stating that a repository carrying
neither needs nothing extra so absence does not send an agent looking.

Precedence is itself a gate and is written as one: a repository governs how work
is done, never whether it is authorized.

## Delivery is a skill, and the order says what to deliver

"Deliver the changes" was procedure an agent had to assemble from a resident
paragraph each time, and the session shows what that costs: a request opened
against the wrong branch is one confident sentence away at any moment.
`cc-deliver` now carries it, loaded by the words that precede it — deliver, open
a pull request.

It carries procedure only. The request is what authorizes push and request
creation, merging is still separate, and the skill says so. It covers every
shape the work comes in: a branch in a bound checkout after direct execution, one
plan's branch in each repository it names, and the chain ends of a run of several
plans.

`record order` gains `deliver` on each plan: the repositories whose chain ends at
that plan, and therefore the branches a pull request should open from. It is
derived at order time, never written to a record, so it cannot disagree with the
dependencies it came from.

The mark is a list of repositories rather than a flag because ancestry is per
repository. A predecessor that does not share a repository contributes nothing to
that repository's branch, so one plan can end a chain in one repository and sit
mid-chain in another — a single boolean would either duplicate work already in a
successor's branch or drop a repository's work entirely.

Reading the last wave is the shortcut that looks right and is not. Waves answer
readiness, so a plan nothing depends on sits in wave 1 and still ends its chain.
On a ten-plan run with two independent roots, the last wave holds one plan and
delivering it drops an entire four-plan chain without saying so.

`cc-dispatch` gains the sentence this exposed: a plan naming several repositories
has a worktree and a branch in each, so it takes one sole-owner worker per
repository rather than one for the plan.

## Two messages that were answering the wrong question

A workspace written by a newer CLI was told `v1 migration is not automatic`,
sending the reader to rewrite a workspace that is not broken. Initialization
already separated the two reasons; loading now does the same.

Completion says what it is not. Completing a plan does not mean its work was
merged: a plan another approach replaced is completed anyway, with a note saying
so. But `record order` treats any plan carrying `completed_at` as a satisfied
dependency, so a plan that merged nothing still satisfies whatever depends on
it, and those dependencies belong on the plan that did the work.

`gitignore` says why role definitions are ignored and that the skills beside them
are not. The ignored paths are `agents/`, not `skills/`, and one directory
holding both makes that easy to misread.

## Record format

Records written by 2.0.0-rc.4 and later are read by this candidate unchanged, and
2.0.0 will read them too. The frontmatter break between 2.0.0-rc.3 and
2.0.0-rc.4 was the last one; a workspace still on 2.0.0-rc.3 or earlier is not
converted and starts fresh.

## Upgrading

Install the CLI, then take this release's `AGENTS.md` and the `.agents/skills/`,
`.claude/skills/`, and `.cursor/skills/` trees into the workspace. An `AGENTS.md`
you customized needs merging rather than replacing.

**Run `agent setup` after installing.** The worker brief changed, and native role
definitions embed it, so a host still holding the previous definitions briefs its
workers with the previous text. A definition you customized is preserved and
reported rather than overwritten.

No records are rewritten, and a workspace left on the previous candidate keeps
working with its previous instruction.

## Candidate status

The layering 2.0.0-rc.9 bet on is no longer only a bet. The recorded session ran
a full lifecycle on Codex — the host with no skill registry, where a skill is
reached only because the entry instruction names its path — and every stage's
skill was loaded when its stage arrived. The gates held throughout: every push,
pull request, merge, and tag waited for a person, and a screenshot pasted into
the session was twice treated as evidence rather than instruction.

That is one host, one operator, one session. **Claude Code and Cursor remain
unexercised**, and no test here establishes that any host loads or follows the
shared instruction.

Deterministic tests cover the new reports in both directions, and the silent
cases are asserted as carefully as the loud ones. The chain-end marks are covered
across waves and linear mode, per repository, and against the wave-number
shortcut they exist to make unreachable. The wording that must not
collapse back to one arbitrary branch is asserted absent from the several-sibling
report. Both schema answers are covered; neither was before.

What no test establishes is the instruction added here. Whether an agent that
cannot verify something says so is exactly the kind of claim a deterministic test
cannot make, and the failure it addresses was a report, not an action. Exercise
the flows you rely on before depending on this release, and read what a session
tells you it did against what it could have done.
