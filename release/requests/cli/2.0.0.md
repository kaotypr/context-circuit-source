# Context Circuit CLI 2.0.0

The native executable behind a Context Circuit workspace. It allocates stable
IDs, edits structured records, records approvals and completion, prepares
isolated Git working copies, derives execution order, and produces deterministic
diagnostics.

What it does not do is decide anything. It holds no model credentials and never
calls a model API, so a capability that needs judgment is a skill or an
instruction change rather than a command. Human authorization sits outside both
and is never inferred by either.

## Installing

Ask the workspace's `cc-cli` skill, which selects the platform, verifies the
download against its checksum, and installs without administrator access.
Binaries are published for macOS, Linux, and Windows on amd64 and arm64.

A workspace pins its expected version in `.context-circuit/CLI_VERSION`, and
installed versions coexist side by side under a version store, so two workspaces
on one machine may expect different releases.

## The command surface

- `init`, `status`, `check` — create a workspace, inspect it, and diagnose it.
  Every `check` finding names what discharges it.
- `member` — add members, set allocation bands, and record the language and
  register a member writes in.
- `repo` — connect, clone, or initialize a repository; set this machine's base
  branch and the shared remote separately; relate repositories to one another.
- `workspace` — bind the Git repository that carries the workspace itself.
- `knowledge` — mount, clone, sync, and list read-only knowledge repositories a
  workspace reads but does not own.
- `record` — create intents and plans with reserved IDs, approve, complete,
  declare dependencies, and derive execution order with `record order`.
- `context find` — search the optional knowledge index, this workspace's and
  any mounted one, marking which side each match came from.
- `worktree` — prepare, inspect, move, repair, and remove isolated working
  copies, reusing ignored runtime files through copy-on-write where the
  filesystem supports it.
- `agent` — inspect and configure per-host subagent model and effort settings,
  write role definitions, and produce a dispatch specification the host launches
  unmodified.
- `template export` — write the blank workspace seed this binary carries.

Every command answers in human text or, with `--json`, in a stable structured
form.

Approval, completion, fetch, and removal are explicit operations whose caller
must hold the user's authorization. No command executes a plan, starts a review,
commits, pushes, merges, deploys, or removes a completed worktree on its own.

## Compatibility

Records written by `2.0.0-rc.4` and later are read unchanged, and 2.0.0 changes
no record format, no schema, and no command surface against `2.0.0-rc.14`.

Unknown fields in structured records are errors, which is why a workspace pins
its CLI version: an older CLI cannot read a workspace using a field introduced
after it. Nothing is removed from a workspace on upgrade.

The embedded workspace seed is a convenience for `init` and `template export`.
It does not make the two products one release — the workspace template has its
own version line and its own tags.
