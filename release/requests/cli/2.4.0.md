# Context Circuit CLI 2.4.0

Every member of a workspace upgrades together. The first changing command 2.4.0
runs in an existing workspace, once setup is complete, splits the shared
`.context-circuit/ids.yaml` into one file per member,
`.context-circuit/ids/<member>.yaml`, and moves `workspace.yaml` from schema 2 to
schema 3. Each reservation goes to the file of its record's author; one with no
author goes to the member selected on that machine. The split is reported as a
notice and changes no command's result. Older CLIs refuse a schema 3 workspace
with "workspace schema 3 requires a newer CLI; this CLI supports schema 2", so
every member needs 2.4.0 before they pull the split. Commit and push it like any
record change.

A shared `ids.yaml` that comes back after the split, for example merged in from
a teammate's 2.3.0 clone, is split again by the next changing command, which
adds only the reservations the member files do not already hold. `check` reports
a number reserved in two member files for a person to fix. Member IDs that are
Windows device names, such as `con` or `nul`, are refused, because no clone on
Windows could check out the ID file they name. A 2.4.0 `init` starts at schema 3
with the first member's own ID file.

Every workspace now has a roster, and every member a band. `init` requires a
member and suggests band 1; the solo workspace with no roster is gone. Band 0 is
a band like any other, `i001`-`i099` and `p0001`-`p0999`. Until the roster lists
a member, every member holds a band, and this machine has selected one, every
changing command is refused with a message naming the missing step; `init`,
`member add`, `member use`, `member band`, and the reading commands still run.
`status` reports `band_required` with a suggested band for each member who has
none, and `next_band` for the next member added. A member whose band 2.3.0
stored as 0 counts as unbanded and is asked to pick one; picking 0 keeps their
old numbering.

`member add` now requires `--band`, and without it the error names the next free
band. `member band --band 0` sets band 0 rather than clearing the member's band,
and a band can no longer be cleared. `record delete --all` works only while the
roster lists exactly one member; otherwise name whose records go with
`--member`. A roster two clones broke is reported by `status` and `check` for a
person to fix, and changing commands are refused until it is: a `members.yaml`
that no longer reads, such as one left with conflict markers, two members on one
band, or a member given two bands.

`record approve` returns `planning_recommended` instead of `planning_required`:
approval records a decision, and planning follows a request for it, which may
arrive with the approval.

After it succeeds, `record approve` checks the intent's file, and
`record complete` the plan's files and its intent's file, wherever they live,
plus every ID file: the shared `.context-circuit/ids.yaml` and each per-member
file. When Git reports any of them uncommitted, the result carries
`commit_recommended` with `files`, each a `path` relative to the workspace root
with `/` separators on every OS and a `change` of `new`, `modified`, or
`deleted`, and a `note` saying committing needs the person's authorization. A
renamed record is its new path `new` and its old path `deleted`; other
uncommitted records are not listed. Both commands rewrite the record they touch,
so in a Git workspace that record is always listed. When Git is not installed or
the workspace is not in a Git repository, the result carries `commit_unchecked`
with the reason instead. The check only adds keys: it never blocks or undoes the
command, and the CLI never stages or commits. A workspace inside another
repository is reported relative to its own root. The Git status reader behind
`status` and `repo inspect` now reads renames, so `changes` lists a renamed file
once, as `R  new/path`, rather than also listing its old path with no code.
This implements #144, reported via #141.

A member may carry an optional `roles` list of free text, set with
`member add --role`, `init --member-role`, or `member roles`, and cleared with
`member roles --clear`. Roles are shown by `member list` and `status` and decide
nothing. They are written only at schema 3. A 2.3.0 `member list` on a roster
with roles fails on the unknown `roles` field rather than asking for an upgrade,
and `check` reports roles found in a schema 2 roster.

`worktree prune --repo ID` drops the plan-to-worktree associations of worktrees
Git no longer lists, and reports them as `dropped`. It touches no worktree,
branch, or file. When `worktree prepare` finds a plan's branch checked out in
another working copy, it now names the branch, where it is checked out, whether
that is a known worktree for the plan, and the safe next steps, and changes
nothing. `check` now points at `worktree prune` rather than `worktree repair`
when Git no longer lists a worktree a plan is associated with, and keeps the
repair advice for a checkout that only moved. The `record delete` refusal for a
plan's worktree names `worktree prune` too.

Thanks to @hallode for `worktree prune` (#140).

For contributors to this repository, CI now runs on pushes to
`development/v2`, and `CONTRIBUTING.md` names it as the branch pull requests
target.
