# Context Circuit 2.0.0-rc.13

A candidate for 2.0.0-rc.12 with two changes: a workspace can mount knowledge it
does not own, and a record written in another language is composed in that
language rather than translated into it. No record changes shape, no existing file moves, and
nothing is converted for you. The v2 description in 2.0.0-rc.1 still stands. This
template recommends CLI `2.0.0-rc.13`. Git is required. No Go or Python runtime
is.

## The knowledge a workspace does not own

`context/` assumes the workspace owns what it describes. That assumption is built
into the loop that keeps it true: completing a plan returns the catalog entries
scoped to that plan's repositories, and the note and its entry move together.
Work done here is what makes a note here wrong, so work done here is what brings
it back for judgment.

An organization's knowledge center breaks every part of that. One repository is
read by many workspaces, it is changed by teams that do not work in any of them,
and no plan completed here will ever invalidate it. It was still knowledge the
agent had to read — how the file service signs an upload, which notification
channels actually exist, what the deployment proxy does — and the product had
nowhere to put it.

So a workspace with one had two moves, and both were bad. Copy the notes into
`context/`, where a duplicate goes stale silently while still reading as current
and nothing in the workspace can tell that it has. Or leave them out, and watch
each agent re-derive facts somebody already wrote down, from source, from
Swagger, from trial and error.

It is mounted instead:

```yaml
# workspace.yaml — shared
knowledge_repositories:
  core-service-knowledge:
    url: git@git.example.com:platform/core-service-knowledge.git
    default_branch: main
    index: index.md
```

```yaml
# repositories.local.yaml — this machine
knowledge:
  core-service-knowledge:
    path: repositories/core-service-knowledge
```

The split is the one every checkout already makes. Where it lives, which branch
everyone reads, and which file maps it are facts the whole team shares; the
checkout path describes one machine. `knowledge clone` puts it under
`repositories/<id>`, beside the working copies and already excluded by the
shipped `.gitignore`, and takes no `--url` for an ID the workspace already
describes — which is what joining a workspace that has one looks like.

### A separate record, not a separate directory

It is not an entry in the `repositories` map, for the reason
`workspace_repository` is not, and that map has now refused two different things
for it. Every consumer of it reads an entry as somewhere work happens: a plan
names repositories, a relationship joins two, a worktree is cut from one, and
`record order` derives waves across them. None of those is ever what a knowledge
repository means. It records no base branch, because work never starts in it.

The checkout is another matter, and it lands in `repositories/` with the rest.
What separates knowledge from work is the record, not the directory, and a
directory of its own would only assert a separation the record already makes —
while adding a second place to look for a checkout and a second line to ignore.

The two maps do share one ID namespace. A note's anchor names a repository by ID
— `api@internal/billing/dunning/` — so an ID meaning two things makes every
anchor carrying it ambiguous. That is also what makes one directory safe: no
knowledge ID can collide with a repository's, so no checkout can collide either.
Connecting an ID the other side already holds is refused in both directions, and
so is mounting a checkout that is already bound as a repository where work
happens.

### Read-only is enforced, not requested

Obtaining one disables its push URL, and every sync reasserts that, so a checkout
obtained before this existed and one whose push URL was restored by hand both end
up read-only again. A push fails against `READ-ONLY-KNOWLEDGE-REPOSITORY` rather
than half-succeeding, and Git echoes that back, so the refusal explains itself at
the moment someone tries rather than in documentation they did not read.

This is deliberate, and it is the one place in this product where a rule is
mechanical rather than written. Almost every other boundary here is conditional —
read the exact source files the task names, commit here but not there — and a
condition cannot be a Git setting. "Never write to a repository this workspace
does not own" has no conditions in it, so it does not need an agent to remember
it.

An improvement goes upstream through that repository's own review, from a
separate checkout of it. That is slower than editing in place, and it is the
point: an edit that lands only here helps nobody and is lost on the next
fast-forward.

### Sync fetches, then fast-forwards only when it is safe

`knowledge sync` fetches, then fast-forwards to the shared branch — and only when
the checkout is clean and on it. It never merges, rebases, resets, or discards.

A checkout holding uncommitted work is reported and left exactly as it is. A
checkout holding commits, where the upstream has also moved, is reported as
diverged and left exactly as it is. Both say plainly that nothing was changed,
and both name where the work should go instead. Moving somebody's work is not a
decision this command has standing to make, and a sync that quietly resolved it
would be indistinguishable from a sync that ate it.

### Retrieval reads both, and says which is which

`context find --query` now searches this workspace's catalog and every mounted
index, and marks each match with the source it came from and whether it is
borrowed. That mark is the whole difference between an entry to edit and one to
raise upstream.

It also reports any index it could not read, rather than returning a shorter
list. A borrowed index this machine has not obtained would otherwise narrow the
result in silence, and a search that found nothing reads identically to one that
never looked — which is the confident miss the catalog exists to prevent.

A borrowed repository writes its index its own way. Matching stays plain
case-insensitive substring over whole lines, so an index in some other project's
format is searched as it is rather than parsed as this product's catalog and
found empty.

### What `check` says, and what it deliberately does not

`check` reports what stands between this machine and reading the knowledge: a
repository nobody here has obtained, naming the command that obtains it; a
checkout with local edits in a repository that is read-only here; one sitting on
a branch nobody else reads; one behind its remote as of the last fetch; and a
recorded index that cannot be read, or was never recorded at all.

It reports nothing about the content. The catalog rules — one note one entry, a
reviewed date, anchors in an `Owner:` block, a heading that says what belongs
under it — exist so that a person here can fix what they break. Neither half is
true of a repository this workspace does not own, and a diagnostic that reported
faults nobody may correct would stop being worth reading.

For the same reason, completion never names a borrowed entry as knowledge to
reconcile. `reconcile_required` is an obligation, and an obligation nobody here
can discharge is noise. Borrowed knowledge goes stale on its owner's schedule;
when you find it wrong, say so and raise it upstream.

## A record in another language was English wearing other words

2.0.0-rc.12 decided which language a record is written in. It decided nothing
about how that language is written, and the gap showed in the first Indonesian
intents: grammatical, precise, and stiff — English sentences with Indonesian
vocabulary.

The symptoms were consistent. English clause architecture survived the crossing,
so a sentence hinging on `, so` stayed one sentence where Indonesian would use
two. Nominalizations came across intact — "no change to how the current quarter
is determined" is ordinary English and heavy almost everywhere else. Technical
vocabulary was translated inconsistently, keeping `cache` and `backend` while
rendering `refresh` as `penyegaran`. And the register drifted without anyone
choosing to move it: words that are neutral in English land as bureaucratic when
carried across literally, so plain English became formal Indonesian.

Underneath all four, the product prescribed *how to write* only for English.
`cc-knowledge` carries a style section whose thresholds 2.0.0-rc.12 admitted were
"calibrated by measuring an English tree", and everything else reached another
language through a translation step nobody had described.

### The structure is English whatever the prose is

`Goal`, `Non-goals`, `Constraints`, `Success criteria`, `Repository scope`, and
`Open questions` are the record's shape, not its content — the same category as
`created_by`, the slug, and the dates, all of which the language table already
pins as unchanged. They were being translated because nothing said they were
structure.

Three costs. Two members produce differently-shaped records, so a reader no
longer knows where to look. The translation itself drifts — `Bukan tujuan` in one
session, `Di luar cakupan` in the next — and a field name that varies per
generation is not a field name. And nothing can find them: nothing parses
headings today, but the catalog already learned this exact lesson, and is English
because substring search over a mixed-language index quietly breaks.

The language table gains the row, and the entry instruction says why.

### Compose in the language rather than into it

`cc-intent` carries the procedure, and `cc-plan` the short form: let sentence
structure follow the target language rather than preserving English clause order
and length, prefer the verb where English would nominalize, and keep technical
vocabulary in the form engineers in that language actually say — consistently,
because half-translated technical prose reads worse than either choice made
whole.

Each rule names an operation rather than a virtue, because "write naturally"
gives a model nothing to apply while "split a sentence that keeps an English
hinge" does.

The skill carries no worked examples, and that is a deliberate limit rather than
an omission. An example is necessarily in one language, and `cc-intent` loads for
every member whatever they write in; three Indonesian pairs are guidance to one
team and noise to the next, with a real risk of anchoring an agent on conventions
that belong to a language it is not writing. A team that wants specifics records
a `tone` instead, which is the mechanism for exactly that and reaches only the
members it describes.

### A team can say what register it wants

A member may record one beside their language:

```yaml
members:
  kao:
    name: Kao
    language: Bahasa Indonesia
    tone: semi-formal; keep technical terms in English
```

One line of prose, quoted into the instruction that writes a record rather than
parsed — recorded exactly as `language` is, and for the reason that field gives:
the only reader is a sentence quoting it, and a tag would need a table that is
wrong for the first register it omits.

It is per member rather than per workspace because a register is meaningless
without the language it applies to, and the language is already per member.
Unset leaves the general guidance to decide, which is what every record written
before this assumed. The product ships no register default for any language:
Context Circuit cannot have a considered opinion about every language, and two
teams writing the same one will want different answers.

## One command group is new

```
knowledge connect|clone|sync|remote|list
member tone
```

`member add` takes an optional `--tone`, and `member tone --clear` removes a
recorded one — prose has no sentinel the way `member band --band 0` clears a
band.

`context find --query` returns a different shape: matches carrying a source and a
`borrowed` flag, beside the indexes it could not read. A caller reading the
previous flat list of lines needs updating. `context find --repo` is unchanged.
`status` gains a `knowledge_repositories` section when a workspace has any. No
other command changed, and no command commits, pushes, or merges anything.

## Record format

Records written by 2.0.0-rc.4 and later are read by this candidate unchanged.
`knowledge_repositories` and the `knowledge` binding are optional: a workspace
from 2.0.0-rc.12 loads without them, and a workspace that never mounts one never
grows either key. A member's `tone` is optional in the same way, and no record
written by an earlier candidate is rewritten — an intent carrying translated
headings keeps them, because rewriting an approved record to match a new
convention is not worth what it costs.

An older CLI cannot read a workspace that has them. Unknown fields in structured
records are errors, which is the existing contract and the reason each workspace
pins its CLI version.

## Upgrading

Install the CLI, then take this release's `AGENTS.md` and the `.agents/skills/`,
`.claude/skills/`, and `.cursor/skills/` trees into the workspace. An `AGENTS.md`
you customized needs merging rather than replacing; the paragraph that changed is
in **Shared knowledge**. No skill directory is new, and no ignore rule changes:
a mounted checkout lands in `repositories/`, which every workspace already
excludes.

Nothing is required. A workspace with no knowledge center to mount does nothing
differently, and no existing file changes until someone runs a `knowledge`
command.

To mount one:

```sh
context-circuit-cli --workspace <root> knowledge clone --id core-service-knowledge --url GIT_URL
```

On another machine, clone or connect the same ID and pass no URL. `agent setup`
is not required by this release: no role definition changed, and a worker never
reads borrowed knowledge or writes a record, because it works inside a
repository worktree under that repository's instructions.

Nothing needs setting for tone either. A team happy with the general guidance
records nothing; a team that knows the register it wants says so once:

```sh
context-circuit-cli --workspace <root> member tone --id ID --tone 'semi-formal; keep technical terms in English'
```

## Candidate status

Deterministic tests cover the mount end to end. Obtaining one lands at the
default path, writes the shared record with its detected index, writes the
binding to the local file, disables the push URL, and an actual `git push`
against it fails. Retrieval returns a borrowed match carrying its source and
flag. A borrowed entry naming a repository in this workspace's own `{api}` form
is asserted *not* to appear among the entries offered for reconciliation, which
is the case where the two knowledge layers are easiest to confuse.

Sync is covered in four states with the files checked afterwards: current, a real
fast-forward that brings the upstream change in, a dirty checkout that reports
and keeps the uncommitted file, and a diverged checkout that reports and keeps
the local commit. The ID namespace is covered in both directions, plus mounting a
checkout already bound as a repository. `check` is covered for the missing
checkout, asserting the finding names the command that fixes it.

For tone, the mechanical half is covered: the register round-trips into
`members.yaml` and back out of `member list`, `member add` carries it, `--clear`
removes it and leaves the language alone, and it is refused when it stops being
one usable line — empty without `--clear`, both flags at once, an unknown
member, several lines, an essay. The structure rule is asserted present in the
entry instruction by name, and both record-writing skills are asserted to carry
the composition rules, with `cc-intent` asserted to carry the contrastive
examples rather than the rule alone.

What no test here establishes is the premise. Nothing measures whether an agent
actually reads a mounted knowledge center before re-deriving a fact from source —
that is the failure this exists to prevent, it is reported rather than observed,
and it rests on an instruction being followed. Nothing measures whether an agent
refrains from copying a borrowed note into `context/`; the copy is prohibited in
the entry instruction and in `cc-knowledge`, and unlike the write, it is not
mechanically prevented, because a file written into `context/` is an ordinary
file write.

Whether any of the tone guidance changes what a model writes is not measured and
cannot be measured here. It is a claim about prose quality in a language this
product's tests do not read, resting on an instruction being followed — and more
weakly than the language rule it sits beside, because a register is softer than
a rule, and because the guidance is deliberately general where a worked example
would have been specific. What a green suite establishes is that the field
arrives where the writing happens, not that the writing improved. This candidate
leans on the model's own command of the language; read the next record and judge
it.

The mount has been exercised only against fixture repositories, not against a
real knowledge center of any size. Retrieval reads one index file per mounted
repository; a knowledge center whose index does not list everything, or whose
entry point is a directory rather than a file, is not served by this and will
report an index it cannot read. Exercise the flows you rely on before depending
on this release.
