# Nine positive journeys

## Fresh-project journeys

### 1. Initialize a new workspace

An empty directory plus a project name and purpose becomes a valid oriented
workspace. Only the coordinator runs. The result explains what now exists and
does not invent a repository or intent.

### 2. Initialize and create an intent

An empty directory plus project identity and one requested outcome becomes an
initialized workspace with a valid draft intent. Only the coordinator runs and
no implementation repository is modified.

### 3. Create a complete system design

An initialized workspace and explicitly named detailed product brief produce
coherent product-level system design material and separate intents for genuinely
separate decisions. The named brief is an explicit context expansion; unrelated
sources remain outside the envelope.

## Context-gathering journeys

### 4. Gather Product Knowledge from a PRD

An initialized workspace and one named PRD produce indexed living Product
Knowledge with durable provenance. The coordinator reads only relevant existing
knowledge and the named evidence; the source remains unchanged.

### 5. Gather Product Knowledge from an active repository

An initialized workspace connected to one realistic Git repository produces
durable architecture and behavior knowledge. The repository named by the human
is the exact expanded read surface and remains unchanged.

### 6. Combine a PRD with an active repository

Compatible named product requirements and one connected implementation are
synthesized into coherent indexed knowledge. The expansion covers exactly those
two evidence targets and stops after durable knowledge is recorded.

## Intent, planning, and execution journeys

### 7. Create an intent from an established workspace

Accepted Product Knowledge grounds a draft intent for a requested feature. The
coordinator uses the index, selected knowledge, and intent procedure without
reading or changing target code.

### 8. Approve an intent and create a plan

A valid draft intent receives explicit human approval. The coordinator freezes
the decision and launches one real planner child for the named repository. The
planner reads its bounded packet and repository, establishes feasibility, and
publishes a grounded plan without executing it.

### 9. Execute and verify a Standard plan

A valid approved intent and executable plan lead the coordinator to launch one
real worker in its isolated worktree. The worker implements and commits the
change. A separate real read-only verifier inspects the committed result and
returns candidate-bound passing evidence. Each role remains inside its declared
context envelope.
