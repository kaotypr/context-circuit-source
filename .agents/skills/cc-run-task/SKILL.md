---
name: cc-run-task
description: Prepare and coordinate explicitly selected direct or approved-plan work across one or more isolated Git worktrees, with scoped worker and verifier inputs.
---

# Run task

1. Use the canonical `$cc-gather-context` skill to read `AGENTS.md`, `WORKFLOW.md`,
   `workspace.yaml`, the direct request or authoritative approved plan, and relevant repository instructions.
2. Require a concrete requested outcome, overall acceptance, repository-specific acceptance evidence, an implementation scope and test expectation, and registered repositories. For cross-repository work, require one shared-contract owner, contract paths, and an acyclic dependency graph in which every implementation repository depends on the contract owner. Contract-owner criteria must be independently provable before dependent implementation begins.
3. Discover only activity capabilities actually available in the current host. For one planless repository, run `node .agents/bin/cc.mjs run-task --request <text> --repository <name> --acceptance <criterion> --scope <path> --test-scope <test-path>`. For contract-first or approved-plan work, validate and pass a `run-task-request` JSON file with `node .agents/bin/cc.mjs run-task --request-file <path>`. A plan request must select exactly one stable, dependency-free work ID and repeat the authoritative plan reference, version, and approval digest. The command derives repository, scope, tests, verification, and acceptance from the approved execution contract in the numbered plan; repository must be an exact current `workspace.yaml` key and is never inferred from descriptive area text. It rejects caller overrides, draft or stale plans, unknown items, and dependent items before creating runtime state. Add one `--available <capability>` per discovered capability. Never infer availability from configuration alone.
4. If `task.starting` is pending, do not create a worktree. Perform pending descriptions through an authorized session MCP/CLI and record confirmed results with `node .agents/bin/cc.mjs record-lifecycle-action --run-id <id> --event task.starting --action <id> --status <completed|failed> --evidence <text> [--reference <ref>]`. Present `manual_fallbacks` exactly. After completion, run `node .agents/bin/cc.mjs run-task --resume-run <id>` to recheck repository cleanliness and the base commit before worktree creation.
5. Stop on dirty-repository, required-action, ownership, or validation failure. Never reset, stash, clean, or delete work to bypass protection.
6. Read the emitted manifest and repository inputs. Launch only repositories whose input says `ready: true`; a `waiting` repository must remain untouched. Record `worker-started` with `node .agents/bin/cc.mjs record-result --run-id <id> --repository <name> --stage worker-started`, then use the current host's adapter to launch a fresh worker only in the emitted worktree.
7. Require the worker to follow the task's test expectation and save its result at the specified path, then record `worker-result` with the same command. Stop if validation, scope, required-test, identity, commit, or worktree checks fail.
8. Launch a different fresh, read-only verifier with the emitted verifier input. Do not let it repair findings. After a dependency passes, reread the manifest and dependent worker inputs; the recorder unlocks them only when all declared dependencies have independently passed.
   For a plan-linked run, the manifest records its one selected work ID. It remains `pending` until that item's verifier records a pass, fail, or blocked result; siblings and later dependencies are never marked complete.
9. Require the verifier to save its result at the specified path, then record `verifier-result`. If it fails, run `node .agents/bin/cc.mjs prepare-repair --run-id <id> --repository <name>`. Give only the emitted repair-worker input to a fresh session, record its worker result, and rerun a different fresh verifier. Never let the verifier repair its own findings.
10. Repeat step 9 only while the deterministic command reports another prepared attempt. When the configured maximum is exhausted, it records a blocked outcome; preserve the worktree and report the escalation instead of continuing.
11. After every repository has a passing verdict and the manifest is `passed`, run `node .agents/bin/cc.mjs prepare-review --run-id <id> --repository <name>` for each repository. Present its exact cwd, argv, and shell-rendered diff, commit, show, test, target-switch, and human merge commands. Recorded verifier commands remain intact and run from the emitted product worktree cwd; do not parse or reconstruct their shell syntax. `ready-for-local-review` is actionable and is not blocked by a missing remote. Only a `ready-for-publication` handoff may be remotely published, and only after explicit authorization. Push only the emitted branch and use an available authenticated `gh` or `glab` command to open a draft pull request from the emitted title/body. Record only the confirmed response with `node .agents/bin/cc.mjs record-review-publication --run-id <id> --repository <name> --status published --tool <gh|glab|manual> --pull-request <ref> --evidence <single-line evidence> --authorized`. Record an authorized confirmed failure with `--status failed`, no reference, and `--authorized`; without authorization preserve the branch and do not create a publication record.
12. Run `node .agents/bin/cc.mjs prepare-lifecycle --run-id <id> --event task.review-ready`, complete its recorded actions using the confirmed pull-request reference when applicable, and only then present the handoffs.

Only the coordinator may perform explicitly configured lifecycle actions and authorized draft-PR publication. Workers and verifiers never mutate activity state. Never merge, deploy, or clean runtime evidence automatically. Review preparation records only the remote name, never a credential-bearing URL.
After the human merges, use the handoff's exact `confirm-merge` command. It must prove the reviewed head is reachable through the reported merge commit from the configured default target before presenting its exact `finish-work` guidance. The agent never executes the merge command.
