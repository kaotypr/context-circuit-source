## Intended behavior

The thread kind adds a second publication onto the existing cc-publish backbone: on
`/cc-publish <plan-id>` against a `kind: thread` publication, it reads a plan's open
questions (INV-PLAN-04, `reads: [plans]`) and posts a `[thread]`-prefixed parent
message plus one fully-described threaded reply per open question. It is one-way,
manual, self-contained, and discussion-safe: on re-run it edits only its own
messages and appends replies for new questions, never touching or deleting a human
reply.

## Concrete change and affected surfaces

Author `wrapper/contracts/schemas/publication-thread-record.yaml` for the thread
record keyed by the thread and its questions: `plan`, `provider`, a `thread` block
(`channel`, `parent_ts`, `url`), and a `questions` list of `{ ref, reply_ts }`
where `ref` is a stable per-question key derived from the question. Add the thread
branch to `.agents/skills/cc-publish/SKILL.md`: the parent-plus-one-reply-per-
question mapping, the `[thread] [<plan-number>] <plan title> — open questions`
headline, self-contained fully-described replies following `instructions`, and
discussion-safe idempotency (edit own messages, append for new questions, never
delete, optionally add a "resolved" note for a no-longer-open question).

## Inputs and outputs

Inputs: `config.yaml`, the plan's open questions, and the prior thread record (if
any), with chat calls via host/MCP. Outputs: a chat parent message and per-question
replies, and an updated thread record under `publication/<name>/published/`. No
human reply is ever read back into the workspace.

## Risks and open questions

- Idempotency here differs from the plan kind: it must never clobber a discussion,
  so it edits only its own messages and never deletes any message.
- Slack is first (parent `ts` is the thread root, replies set `thread_ts`); other
  chat providers reuse the same shape keyed by their returned id.
