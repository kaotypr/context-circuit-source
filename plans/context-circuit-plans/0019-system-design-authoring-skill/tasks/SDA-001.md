## Intended behavior

Ship a single read-as-procedure skill, `cc-system-design`, that teaches an agent to
author and structure a system design as source material under
`sources/system-design/<product>/<version>/<scope>/`. Its payload is the authoring
rubric: location, the three-tier layout (README index, normative `design.md`,
detail files/sub-folders as concerns grow), the detail-per-file altitude rule,
scale-triggered splitting, scope-by-concern separation (never one folder per git
repo), and embedded fenced mermaid. It adds no lifecycle, status, gate, runtime,
schema, invariant, or WORKFLOW action.

## Concrete change and affected surfaces

Author `.agents/skills/cc-system-design/SKILL.md` carrying the full rubric and
pointing authors at this repo's own `sources/system-design/context-circuit/` as the
dogfooded reference. Apply the four coordinated allowlist updates exactly as
`cc-run-stack` did: add `required .agents/skills/cc-system-design/SKILL.md` to
`scripts/release-manifest.txt`; add `cc-system-design` to the shipped-skill
allowlist in `scripts/release-artifact.sh`; add it to the allowlist and bump the
shipped-skill count in `test/release/test-release.sh`; and add it to the
required-skill list in `test/contracts/test-contracts.sh`.

## Inputs and outputs

Inputs: the authoring rubric and the existing release/allowlist wiring. Outputs: the
shipped skill file plus the four allowlist edits so the skill ships in the template
and is resolved only by path (INV-SKILL-01). No runtime function, record, schema,
invariant, WORKFLOW action, or first-class `design/` area is added.

## Risks and open questions

- The skill must only draft structured source files: it never approves, accepts,
  plans, executes, or writes Product Knowledge, and it must not pre-fragment a small
  design into many near-empty files.

## Stop conditions

- Do not expand scope beyond the declared repositories and paths.
