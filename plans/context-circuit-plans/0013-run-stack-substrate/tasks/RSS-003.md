## Intended behavior

When a plan becomes runnable, the runtime selects its base per repository before
the worker starts: the anchor tip when there are no same-repo predecessors, the
single predecessor branch when there is exactly one, or a runtime-authored
integration merge of the predecessor branches when there are two or more
(INV-CONCURRENCY-02). The integration merge is authored by the runtime — never the
worker — and is never counted as a worker attempt; a base that cannot be built
cleanly is a blocked execution, not a worker failure.

## Concrete change and affected surfaces

Add optional `based_on` to the per-repository record in
`wrapper/contracts/schemas/execution.yaml` and broaden `base_commit` to allow a
runtime-authored integration merge (schema stays version 1). In
`wrapper/runtime/engine.sh` implement base selection: build the integration merge
on the plan's own branch in its own worktree before handoff, record
`based_on`/`base_commit`, and keep any named base ref in the reserved namespace
`refs/cc-base/<plan>/<repo>`, never nested beneath a branch ref. Rebuild a stale
base from the predecessor's new branch tip when a predecessor is repaired.

## Inputs and outputs

Inputs: the plan's same-repo predecessor branches, the anchor tip, and
predecessor repair state. Outputs: the selected base recorded as
`based_on`/`base_commit` in the execution record, the runtime-authored integration
merge commit (first ancestor of the plan's branch), optional
`refs/cc-base/<plan>/<repo>` refs, and a blocked outcome when the base cannot be
built cleanly.

## Risks and open questions

- Disjoint leases make concurrent predecessors clean by construction; if a stale
  base persisted across a predecessor repair it would verify work against the
  wrong world, so rebuild must be reliable.
