## Intended behavior

A plan in the stack becomes runnable only when both gates open: every plan
dependency is `verified` and every path region it needs is free (no overlapping
non-descendant lease) in each repository — an AND-join. The runtime evaluates
readiness and leases deterministically and drives the ready set through the
unchanged v0.5 worker/verifier/repair cycle. A failed or blocked plan holds only
its descendants in the dependency graph; unrelated verified siblings are
untouched, so a failure prunes a branch rather than the whole run.

## Concrete change and affected surfaces

In `wrapper/runtime/engine.sh` add deterministic readiness evaluation
(`dependencies verified AND leases_free(repo, allowed_paths)`) and the scheduling
loop that computes the ready set, acquires leases, selects the base, and runs each
plan. On `verified` hold leases until delivery and unblock descendants; on
`failed` or `blocked` preserve evidence and keep descendants held while sparing
siblings. The runtime detects readiness only; the coordinator decides launch
concurrency (INV-RUNTIME-01), and the runtime contains no scheduling heuristic.

## Inputs and outputs

Inputs: the stack of approved plans, per-plan dependency and lease state, and
worker/verifier outcomes. Outputs: the computed ready set each iteration, lease
acquisition, per-plan terminal states (verified / failed / blocked / held), and
descendant-only containment of failures.

## Risks and open questions

- Single-repository fan-in (many plans feeding one integrating plan) widens the
  blast radius; the mitigation is structural (keep the fan-in plan late and thin),
  not a runtime change.
- A missing host child capability yields `host-blocked`, which is not a worker
  failure.
