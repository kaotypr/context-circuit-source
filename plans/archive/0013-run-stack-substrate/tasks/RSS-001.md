## Intended behavior

A plan may declare optional inter-plan `plan_dependencies` (a list of `{id, reason}`),
distinct from the intra-plan task `depends_on`. Because the field is load-bearing —
an older engine that ignored it would schedule a plan without its dependencies —
a plan that declares it must set `schema_version: 2`, and this plan owns the
coordinated v0.6 bump so a v0.5 engine refuses such a plan instead of
mis-scheduling it. Plans that do not use the field stay `schema_version: 1` and
read identically to both engines.

## Concrete change and affected surfaces

Add optional `plan_dependencies` to `wrapper/contracts/schemas/plan.yaml` with the
rule that its presence requires `schema_version: 2`. In `wrapper/manifest.yaml`
set `accepted_schema_versions.plan: [1, 2]` and `runtime_version: 0.6.0`. In
`wrapper/runtime/engine.sh` validate that each dependency entry references an
existing plan ID in the workspace, is non-self, and that the dependency graph
across the stack is acyclic (INV-PLAN-05).

## Inputs and outputs

Inputs: `plan.yaml` instances (with or without `plan_dependencies`), the workspace
set of plan IDs. Outputs: an accepted or rejected plan contract, the bumped
manifest (`runtime_version 0.6.0`, plan schema `[1, 2]`), and deterministic
validation results for missing-schema-2, cyclic, unknown, and self references.
