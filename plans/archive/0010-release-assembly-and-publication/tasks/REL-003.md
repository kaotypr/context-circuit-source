## Intended behavior

Publication is a deliberate, workflow-only act that runs the full acceptance
suite as its gate before assembling, then stamps the published template release
version and writes it into the template repository as exactly one commit plus one
annotated tag. The runtime never pushes or publishes (INV-RUNTIME-01), and no AI
attribution, credential, or provider payload ever reaches the published commit,
tag, release notes, or artifact (INV-SEC-01, no-attribution rule).

## Concrete change and affected surfaces

Implement `scripts/publish-template.sh` to run `sh test/acceptance.sh` as the
publish gate, then assemble via the REL-002 assembler, stamp
`template_version` in `wrapper/manifest.yaml`, and produce one
`chore(release): v<version>` commit and a `v<version>` tag authored as the human
maintainer only. Implement `scripts/resolve-release-version.sh` to resolve
exactly one target version from the release ledger request (failing loudly on
ambiguity). Wire `test/acceptance.sh` as the gate and add
`test/release/test-publish.sh` to verify the gate ordering and attribution/secret
hygiene. Independent semantic version line starts at `0.0.1-alpha.1`.

## Inputs and outputs

Inputs: the assembled artifact, the acceptance suite result, and the release
ledger request (`release/requests/<version>.md`). Outputs: a resolved release
version, a single stamped release commit and annotated tag, and release notes,
all free of attribution and credentials.

## Risks and open questions

- Assembly must never run before the acceptance suite passes, or REL-AC-04 is
  violated.
- Attribution or a stamped credential leaking into the commit/tag/release body
  breaks REL-AC-05; the version stamp must be normalized so the diff-gate
  reflects real content changes only.
