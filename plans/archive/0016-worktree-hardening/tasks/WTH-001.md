## Intended behavior

Worktree hardening prepares an isolated execution worktree so the
execution-environment workarounds that once cluttered hand-written prompts
(symlinked deps, verify-deps flags, hook bypasses) become unnecessary rather than
documented (INV-GROUND-03). Deterministically and host-neutral, the runtime
detects the toolchain from lockfiles/manifests via a runtime-constant table,
provisions dependencies (reusing the bound checkout where the ecosystem allows),
handles commit hooks for the isolated context, and reports the result honestly as
the manifest `environment` field (`ready` or `no-toolchain`).

## Concrete change and affected surfaces

In `wrapper/runtime/engine.sh` add worktree-hardening functions: toolchain
detection (table lookup from known lockfiles/manifests to a provisioning
strategy), dependency provisioning that gives the writer a working environment
without a per-worktree install and configures the tool so its own preflight does
not abort, commit-hook handling for the runtime-owned commit step, and setting the
manifest `environment` field. Isolation is unchanged — each execution still gets
its own worktree and branch; hardening only makes that worktree ready.

## Inputs and outputs

Inputs: the prepared worktree, its lockfiles/manifests, the bound checkout's
installed dependencies. Outputs: a hardened, ready worktree (deps provisioned,
hooks handled), the `environment` field set to `ready` or `no-toolchain`, and any
residual toolchain hint only as a runtime-generated cache, never a user-authored
file.

## Risks and open questions

- Hardening removes only CC-induced friction; genuinely repo-specific build/test/
  lint detail stays in the repo's own docs and reaches the writer via discovery.
- Provisioning and hook handling must remain deterministic and host-neutral with no
  network policy beyond what the ecosystem's provisioning already implies.
